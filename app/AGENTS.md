# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable product decisions

- Treat `../PRD.md` and `../import-template.csv` as the product source of truth.
- This is one responsive web application, not separate mobile and desktop products.
- The public visual reference is `../docs/recordshelf-preview.png`; private design-history captures remain local-only.
- Preserve the cover-first warm-white visual system: near-black type, cool gray metadata, restrained violet active states, amber ratings, tiny cover radii, hairline dividers, and almost no shadow.
- The user-supplied black-and-white `record` mark is the single brand source for the desktop sidebar, browser favicon/touch icon, and packaged macOS app/DMG icon. Keep the logo artwork intact; derive platform sizes from `public/recordshelf-logo.png` / `electron/assets/RecordShelf.png` rather than redrawing it with UI icons.
- Mobile uses bottom navigation and a three-column cover grid; desktop uses a slim left navigation and a six-to-seven-column cover grid.
- The library offers a fourth `shelf` view alongside grid, list, and wall. It uses five real releases per proportional, container-fitted spatial shelf on desktop and continuous stacked Cover Flow groups on narrow screens. On narrow screens every resting cover in a group uses the same dimensions and scale; only the hovered or keyboard-focused cover enlarges, temporarily opens clear space above and below itself, and reveals its caption. The shelf inherits the library background, has no large promotional headline, does not leave large gaps between mobile groups, preserves the current filtered/sorted order and infinite pagination, and opens the existing release detail rather than introducing a separate detail experience.
- Mobile detail-header icon-only actions use a fixed 44 × 44 hit target with the SVG centered independently of the hidden text baseline.
- The release listening timeline is newest-first by the entry's real listening date, with rated/marked/updated/created timestamps used only as non-destructive ordering fallbacks. Keep the rail and violet nodes hidden, with no leftover indentation, when there is only one entry; show them only for two or more entries.
- “聆听指南” belongs inside the existing release detail drawer, after the listening timeline and before the manual duplicate-correction panel. Every stable Release ID gets one shared local cache record: the initial full-library migration backfills existing releases once, and each NeoDB sync creates missing records or updates public identity snapshots for newly added/changed releases. Normal sync never re-researches or rewrites an existing successful guide; only the user's explicit refresh may do that. When no research provider or adequate evidence exists, persist `INSUFFICIENT_SOURCES` with an empty article rather than filler. An empty/insufficient guide shows no placeholder card or staged-rollout message: keep only the section title, privacy note, and a 44 × 44 top-right refresh icon that explicitly starts research for that release. During a user-started Codex refresh, show elapsed time plus the safe stages “准备资料 / 联网检索 / 核验来源 / 撰写指南 / 写入本地”; never reveal raw chain-of-thought. Reopening the detail restores the running job, and completion replaces and expands the guide in place. Match the existing warm-white typography, restrained violet actions, gray metadata and hairline dividers; reference visuals inform the edge-to-edge reading rhythm only and must not introduce a separate dark, gradient, glass or promotional visual system. Professional reviews, community response and source links stay visibly distinguishable.
- Listening-guide provider credentials are local secrets, never library data. OpenAI and Google Gemini are trusted built-in presets: save their keys separately at `~/Library/Application Support/RecordShelf/openai-api-key` and `~/Library/Application Support/RecordShelf/gemini-api-key` with mode `0600`; save only active provider/model metadata in the same private directory. Allow `OPENAI_API_KEY` and `GEMINI_API_KEY`/`GOOGLE_API_KEY` environment overrides, never return saved key plaintext to the UI, and never include credentials in shared state, browser storage, guides, exports, logs, Git, Sites, packaged resources, or build output. Do not accept arbitrary provider base URLs or custom auth headers: every new provider needs a fixed trusted host plus explicit search, structured-output, source-allowlist, and redacted-error adapters. In the local Web and Mac builds, the detail refresh button invokes the locally installed, signed-in Codex CLI in non-interactive read-only mode and never requires or reads an API key. It sends only the public release identity, starts one asynchronous job per release, preserves the previous guide on failure, and persists only actually searched source URLs. For the Owner's private library, the explicit resumable Codex/GPT web-research batch is also the preferred source of listening-guide prose; Gemini is an optional fallback and must never be selected automatically or overwrite a successful Codex guide. Batch research remains a separate user-started maintenance action and is never silently coupled to ordinary NeoDB sync.
- Releases and listening entries are separate entities. Never overwrite historical scores or comments when a new listening entry is created.
- Local development may load an ignored private NeoDB export. In that export, the `info` value is shaped as `artist:<name>`; remove only the leading `artist:` field label and treat the complete remainder as the artist display/grouping name. Production and public builds must use synthetic demo records.
- The release detail drawer shows a 「专辑介绍」module between the platform links and the listening timeline. It always renders so the user can add, edit, or clear their own plain-text `albumIntroduction`, persisted in shared user deltas (`releaseMetadataOverrides` / `userReleases`) and never overwritten by Apple cache or NeoDB sync. When a confirmed Apple Music album URL parses, also load official `editorialNotes` server-side with a MusicKit Developer Token from `APPLE_MUSIC_DEVELOPER_TOKEN` or `Application Support/RecordShelf/apple-music-developer-token` (mode `0600`); quote Apple's prose, never rewrite, summarize, or machine-translate it; "multi-language" means Apple's own localized versions. Parse only `https://music.apple.com/{storefront}/album/…/{numericAlbumId}` with a real URL parser, ignore `?i=<songId>`, and skip the official fetch when no confirmed Apple album link parses. Never scrape `music.apple.com` or reuse page tokens, and keep the token out of the client bundle, logs, responses, and packaged artifacts. Resolve cross-storefront IDs through `filter[equivalents]`, prefer `standard` over `short`, drop empty notes, sanitize official HTML to a `<b>/<i>/<br>` allowlist server-side, and render user-written text as plain text only. Dedupe official notes by normalized plainText hash while merging region/language sources. Do not label user-written notes with 「我写的」 or any author badge; prefer the user copy when present. Cached official notes stay under `Application Support/RecordShelf/apple-music-editorial-notes.json` — they stay out of shared user state and must never overwrite user-written text. Do not grow this into a standalone Apple editorial aggregation, archive, export, or comparison database, and always keep the source label plus the Apple Music entry point.
- The macOS desktop build is a deliberate local-only privacy exception: `npm run build:desktop` may embed `.private/neodb-library.local.json` into ignored `.app`/DMG artifacts, while normal production, Sites, CI, and public builds must continue exporting only demo data. The Electron wrapper serves the same SPA and metadata APIs from fixed origin `127.0.0.1:4173`, uses an ad-hoc local signature, and must never commit desktop artifacts or private data.
- Web development and the macOS wrapper share user deltas through `~/Library/Application Support/RecordShelf/shared-local-state.json`. Bootstrap must hydrate this shared file before React mounts, migrate legacy Web state without letting an empty desktop profile overwrite it, and keep NeoDB access/pending tokens session-only. Release tombstones, manual merge outcomes, artist mappings, duplicate dismissals, filters, and safe sync state belong in the shared file.
- The fixed `127.0.0.1:4173` Web app is the only authoritative browser origin for shared user data; the Mac wrapper is the other writer over that same fixed origin. Port 5173 is retired legacy state: it may hydrate read-only for inspection but must never seed, merge into, overwrite, or otherwise be maintained as a shared-data source. When recovering data, use the newest confirmed 4173 state and never union older-origin deletion or artist decisions into it.
- `~/Library/Application Support/RecordShelf/shared-local-state.json` is the single source of truth once it exists. Both 4173 Web and Mac hydrate from it before mounting and immediately flush every release edit, merge/deletion decision, artist mapping, duplicate dismissal, filter change, and safe NeoDB sync state back to it. Browser localStorage may seed the file only when the shared file is genuinely empty; clearing a migration marker or opening an older profile must never merge stale browser state into a non-empty shared file.
- Shared writes use three-way JSON merging against the client's prior snapshot. Merge distinct stable release/artist/listening-entry IDs, keep the already-newer shared scalar on a true conflict, union tombstones and removal decisions, and never let a legacy migration replace a newer shared entity. Atomically archive the prior revision and retain the latest 20 private recovery snapshots.
- Git commits intentionally exclude the private database and are not data restore points. Before any port merge, persistence rewrite, or desktop migration, create a named non-rotating private checkpoint tied to the migration or commit label. Recover same-origin confirmed user decisions additively: preserve current decisions, restore missing historical identities/aliases, and stop for review on alias or external-ID conflicts. Never use aggregate counts as proof of completeness; verify user-provided sentinel artists and every search alias after recovery.
- The macOS wrapper reserves a 32 px draggable top strip below its hidden-inset title bar. Keep controls outside that strip and preserve it at desktop and narrow responsive widths.
- Preserve NeoDB mark status. A `wishlist` timestamp is a mark date, not a listening or rating date.
- Cover enrichment is exact-link-first: exact Apple Music, exact Spotify oEmbed, NeoDB Open Graph image, then Cover Art Archive. When Apple Music and Spotify agree, their platform consensus outranks a conflicting stale NeoDB OG image. Never accept a fuzzy title-only match.
- Settings includes a user-triggered “更新专辑封面图” local maintenance action. Process empty and client-load-failed covers first, then remote covers that still need local caching; show progress and resolved/unresolved totals. Send providers only confirmed public catalog links/IDs, never ratings, comments, listening dates, shelf state, or artist mappings. A failed old URL must be re-resolved from exact linked providers rather than counted as success. Persist resulting cover paths and provenance as shared Web/Mac metadata deltas; public/Sites builds have no write-capable cover service.
- Apple Music motion artwork is an optional local enhancement, not canonical catalog data. Never batch-scan the library: only a user click inside one release detail may send that release's confirmed public Apple Music album URL to the fixed open-source metadata adapter. Persist available/unavailable evidence and checked time directly in the Web/Mac shared release delta, never ratings, comments, listening dates or artist mappings. When a square Apple HLS resource exists, convert at most 8 seconds locally to an adaptive animated WebP: try 960 px / 10 fps / about quality 80 first, then fall back through 800 px and 720 px profiles only when the generated file exceeds its size budget; keep the final file at or below 8 MB. Store it under `Application Support/RecordShelf/motion-artwork`, and display only this local WebP while the detail is open or a shelf cover is hovered/focused. Respect reduced-motion and fall back silently to the static poster. Do not bundle downloaded motion artwork or the large FFmpeg core into Git, the public/Sites build or the DMG; on the explicit first click, the local server downloads the pinned core once into `Application Support/RecordShelf/motion-runtime` and serves it through a fixed same-origin private route. Undocumented Apple metadata failures must not alter the existing static cover.
- Every release detail keeps NeoDB, Apple Music, Spotify, and motion artwork in one compact icon tool row beside the release-type controls. Never hide the motion entry because an Apple Music link is absent: before a local WebP exists, clicking its icon requests that single release and opens the exact Apple-link editor when required; after a local WebP exists, the icon carries a bottom-right state indicator and toggles motion on/off in place. Do not restore separate platform-link or motion-artwork rows.
- Apple motion downloads in the Mac shell must use Electron `net.fetch` (Chromium's network stack) so system proxy/TUN routing is shared with the visible app. Parse the master and media playlists through that stack, download the single Apple byte-range MP4 locally, then let FFmpeg read only the local file. Do not point standalone FFmpeg or plain Node fetch directly at Apple HLS. Preserve remote-HLS evidence after a network failure and distinguish CDN, HTTP, playlist and conversion errors in the UI.
- External platform ratings stay separate from the owner's listening score and are refreshed only by an explicit single-release action. Never auto-refresh on sync, open, or library load. Resolve Douban only through that release's confirmed NeoDB catalog item and its exact `external_resources`; when several Douban editions are linked, require matching title plus artist or exact date evidence, persist score/count/final URL/check time in the shared release delta, and leave uncertainty blank. The detail “平台评分” panel may save one exact HTTPS album-page link per AOTY, Rate Your Music, Metacritic, and Record Club provider; refresh only those saved links, preserve their native scales, and keep scores/links in the shared private `externalRatings` delta. On user click only: Metacritic and AOTY may be read from the confirmed public album page; Record Club may use the public `api.record.club` path that mirrors the saved album URL. Trust user-confirmed exact links without re-fuzzy-matching local titles. Keep AOTY critic and user scores separately labeled. Rate Your Music stays link-only until an approved automated interface exists. If a fetch is blocked (for example Cloudflare) or empty, retain the previous cached scores, surface a clear status, and never invent substitutes from search snippets or third-party mirrors.
- Local/dev and macOS builds cache resolved covers and serve them at `/private-covers/*`. Dev uses ignored `app/.private/covers/`; the packaged Mac app bundles that folder as `Contents/Resources/covers` and writes newly enriched covers under `~/Library/Application Support/RecordShelf/covers`. `npm run enrich:covers` (default) and CSV `import:neodb` download missing/remote covers and rewrite `coverUrl` to the local route; NeoDB sync queues the same job for new/changed items via `POST /api/local-enrich-covers`. Public/Sites builds must never ship private cover files.
- Prefer the original release-language title from an exact Apple Music, Spotify, or MusicBrainz record. Preserve a differing NeoDB/CSV title as a searchable translated title or alias; never machine-translate the whole library.
- Persist the last exact NeoDB source title. If the same canonical NeoDB item later changes title, promote the new title only when the prior NeoDB title was the primary title, or when a legacy NeoDB URL merges/redirects to a newly titled canonical item; preserve the displaced primary title as an alias and do not overwrite user-confirmed titles.
- In artist search results, split collaboration credits only for matching/grouping. Merge `Artist A/Artist B` releases into the queried artist's section while keeping the full collaboration credit visible on each release.
- Desktop sidebar and mobile bottom navigation contain five primary items and end with “设置”. `/settings` is the extensible settings hub; artist identities live at `/settings/artists`.
- Keep Settings task-oriented: hide future placeholders that have no data or action; label complete JSON download as “备份音乐库” and incremental JSON merge as “导入音乐库备份”, with subtitles that distinguish download from non-destructive import.
- “恢复出厂设置” is a low-emphasis text action at the very bottom of settings, not a prominent danger button. It requires two sequential confirmations, recommends exporting JSON before the final confirmation, and only then clears all browser-local release deltas, artist identities/backups, filters, overrides, NeoDB sync/OAuth state and session token before restoring defaults.
- Artist grouping/search resolves exact normalized aliases to a stable artist identity. Preserve every release's imported full artist credit for display. User-confirmed canonical names, aliases, and MusicBrainz Artist MBIDs are persistent local deltas and must not be overwritten by CSV import or NeoDB sync.
- The default artist page is a paginated lightweight artist index. Do not render every artist's full release grid at once; selecting an artist renders only that identity's releases.
- Artist-index view controls must be functional: the index supports grid and list only; wall is hidden until one artist is selected. A selected artist supports grid, list, and wall over the same release collection.
- Artist identity auditing is evidence-driven. Never fill a MusicBrainz Artist MBID from a name-only search. Require an exact local name/known alias plus at least one exact local release title matching a MusicBrainz Release Group for that Artist. Revalidate existing MBIDs with the same evidence, keep ambiguous/unresolved results unwritten, and report duplicate MBIDs without auto-merging identities.
- Run MusicBrainz identity checks incrementally for new, changed, or 30-day-stale identities, in rate-limited batches with visible progress. Preserve source, matched release titles, status, and checked time.
- Use OpenCC for deterministic simplified/traditional artist-name variants. A user-managed identity may gain source-marked script aliases, but an unmapped credit may be assigned or a new identity auto-created only when the simplified key also has shared exact release-link or full-title evidence. Script similarity alone never merges artists.
- Artist management includes a user-triggered possible-duplicate scan across mapped identities and raw credits. Strong candidates may use the same MusicBrainz Artist MBID, equal normalized full names, OpenCC full-name equality, or a clear Chinese-full-name-plus-Latin-alias structure. General containment and high edit similarity require shared exact release-link or full-title evidence. Never emit a candidate from a shared character fragment alone. Connected strong matches form one review group. Never preselect or auto-merge, keep release credits unchanged, and block quick merging when multiple non-empty MBIDs conflict.
- Mobile artist management is a two-level master-detail flow: the first level is a two-column vertical identity list with no horizontal carousel or expanded editor; tapping an artist opens a dedicated identity editor. Use the single top-left back control to return from detail to the artist list, then from the list to Settings; never render a second inline back action. Desktop keeps the side-by-side list and editor.
- Treat one possible-duplicate scan as a frozen review batch. Confirming or dismissing a group removes only affected candidates, preserves the candidate-list scroll anchor, does not switch the artist editor selection, and never reruns the scan. Only the explicit “重新扫描” action rebuilds and resets the batch.
- Persist “不是同一艺人” candidate keys as shared local decisions so Web and Mac do not resurface the same stable candidate after reopening or rescanning. Factory reset may clear these decisions.
- Empty or missing artist identity IDs are never matching keys. When filtering a frozen duplicate-review batch after a merge, compare only non-empty raw-credit IDs and stable identity IDs so unrelated unmapped candidates remain visible.
- Release-type enrichment must use explicit exact-record evidence from MusicBrainz, NeoDB, Discogs, or an official platform title suffix. Map only Album→LP, EP→EP, and Single→SINGLE; leave ambiguous and other types as `OTHER` for manual editing.
- During NeoDB sync, verify release type only for additions and genuinely changed records. Query only already-linked exact records, never fuzzy-search by title; require all available exact sources to agree, keep conflicts or missing evidence as `OTHER`, and never overwrite a user-confirmed type.
- Release type must be editable quickly from the grid and explicitly from the detail drawer. Persist only user deltas over the bundled library; never write the full 1,833-release catalog to localStorage.
- Manual release creation accepts optional exact NeoDB item, Spotify album, and Apple Music album URLs. Validate each field against its named provider, preserve the filled form on error, store valid links as `CONFIRMED`, and surface them immediately through the existing detail platform buttons.
- Library pagination is automatic: approaching the bottom sentinel loads the next 84 releases. Search, filters, sorting, artist mode, or view changes reset pagination to the first batch.
- NeoDB “同步” is a data-management child under “设置”, not a primary navigation item or personal-profile area. Connect with NeoDB's official read-only OAuth flow, keep the access token session-only, use `/sync` as the child route, and return to `/settings` when the sync panel closes.
- NeoDB sync is incremental by default: read the newest page plus one rotating discovery page, then use NeoDB's official batches of at most 20 item IDs to fingerprint-check every known mark so edits to older-page ratings, comments, times, states, or item metadata are discovered in the same run. Fetch reviews/logs only for changed or newly discovered items, and do a full shelf reconciliation only when the remote count decreases or the user explicitly requests it. Apply additions and updates automatically; require confirmation before removing NeoDB-sourced local records.
- Every successful local NeoDB sync writes a content-addressed CSV snapshot under `Application Support/RecordShelf/neodb-snapshots`. Reuse an existing file when its content is unchanged, retain the latest 20 distinct snapshots, never include OAuth credentials, and keep snapshot failure non-blocking. The snapshot is an audit/recovery artifact; stable NeoDB item IDs and per-row content fingerprints drive reconciliation, while the shared database remains the source of truth.
- NeoDB sync uses progressive feedback: apply and show the core delta first, then run canonical URL auditing and release-type verification as a background phase. Parallelize rotating shelf-page reads. Type verification is eligible only for additions, unclassified releases, or changes to title/source type/exact links/canonical identity; rating, comment, listening-time, and shelf-state-only changes must not query metadata providers. Cache exact type evidence for 30 days by a type-input fingerprint and invalidate it when that fingerprint changes.
- Removal safety overrides fast feedback: never expose a removal candidate from the quick phase. On any full reconciliation, canonicalize every local NeoDB URL first, compare remote and local records by final canonical item ID, and require the same item to be absent in two consecutive full reconciliations before showing a local-removal button. Clear legacy pending removals that were produced without this evidence version.
- NeoDB sync covers all music shelf states (`complete`, `progress`, `wishlist`, and `dropped`) so a non-complete mark is never treated as deleted. Canonicalize legacy NeoDB redirects before identity comparison; a manually resolved or already-known canonical item must update the kept release instead of creating another release. Only a previously unseen canonical NeoDB item may be inserted.
- NeoDB listening-entry identity is semantic, not raw-string based: for the same canonical NeoDB item, normalize timestamps to the same instant and normalize inconsequential comment whitespace before comparing time, rating, comment, and shelf state. Equivalent entries must be kept once (prefer the existing/base entry); genuinely different times, ratings, comments, or states remain separate history.
- Responsive toolbar priority is fixed: when the viewport narrows, hide the “显示 x / y 张发行” result count first; at the next narrower breakpoint hide the LP/EP/Single type tabs and keep sorting plus view switching available through the minimum supported width.
- Release list view keeps NeoDB shelf status in its own column with the exact labels “听过 / 想听 / 在听 / 搁置”. Hide genre and date columns before hiding shelf status at narrow widths.
- Search results prioritize releases: only official release-title or artist-credit matches belong in the primary “唱片与艺人” results. Matches found only in comments, translated titles, aliases, genres, or tags belong in a separate “评论与其他文字” section with the matching text visibly highlighted; never mix these contextual hits into primary release results.
- Library filters use OR within one dimension and AND across different dimensions. Persist applied filters locally, show each condition as a removable chip, use a right drawer on desktop and a bottom sheet on mobile, and keep the same result set across grid/list/wall views.
- Time filtering exposes release date plus one listening-date control (first or latest listen). Do not add a separate marked-date range; legacy saved marked-date filters are discarded during sanitization.
- Existing reliable fields may filter immediately: dates, ratings, comments, listening count, NeoDB shelf state, exact platform links, user-entered values, confirmed artist identities/aliases, local motion-artwork files, user-written album introductions, and persisted listening-guide readiness. External facets such as genres, styles, catalog languages, edition types, release countries, labels, and media formats may appear only when they have user-confirmed or exact-source evidence.
- Completeness shortcuts include missing genre but not missing catalog language. Discard the legacy `MISSING_LANGUAGE` value when sanitizing saved filters.
- Genre enrichment may read only confirmed exact Apple Music album IDs or exact MusicBrainz release/release-group MBIDs. Preserve user genres, skip ambiguous or empty results, store auditable per-source evidence, and show enriched genre chips plus their exact source in release detail.
- The default `enrich:genres` command is limited to a five-record read-only validation. A larger or writing run must include the explicit `--confirm-external-id-lookup` acknowledgement after the Owner approves the displayed provider and ID counts.
- Never infer or persist external facets from titles, cover text, artist nationality, name script, fuzzy candidates, or unverified sources. NeoDB tags remain tags and must never be copied into genres/styles. Catalog language means the language of release and track titles, not sung/lyrics language. Conflicted, rejected, inferred, or unverifiable values stay absent from formal facets and may only be surfaced for manual review.
- Duplicate review is user-driven and lives under “设置 → 疑似重复条目”, not beside library organization tabs. Resolve legacy NeoDB redirects before grouping records by the same final normalized item URL, show each candidate's comment state, and never auto-select a keeper. The settings workflow deletes unselected records without silently moving their history.
- A separate manual merge entry lives at the bottom of every release detail. It accepts a release title, an exact copied internal release ID, an exact same-origin/local RecordShelf `/releases/:id` detail URL, or an exact NeoDB, Apple Music, or Spotify album URL that both records support. Title lookup searches only primary, translated, and alias titles, lists every containment match, and requires the user to choose one candidate before choosing the keeper; title results are never automatic merge evidence. Every release surface exposes a custom desktop context menu on right click and the same action after a deliberate mobile long press so the internal ID can be copied without opening the detail. ID lookup resolves exactly one local record and bypasses shared-platform-link ambiguity. Merging still requires an explicit keeper plus a second confirmation, preserves every link provider already present on the keeper, semantically deduplicates and absorbs unique listening history/comments plus non-conflicting metadata and missing-provider links, then removes the other release. On mobile, each comparison card keeps the selection control and cover on the left, flexible release copy in the middle, and the selected-state indicator inside the right edge; ratings hide first and the selected label collapses to its check icon at the minimum width.
- Release dates must come only from exact linked records (NeoDB structured data, Apple Music lookup, MusicBrainz, or Discogs). Accept a single explicit date or mutually compatible exact dates, preserve precision, and leave conflicts/unresolved dates blank with provenance. Provide both oldest-first and newest-first sorting, with blank dates last in either direction.
